# 跃动健身会员订单管理后台

一个基于 React 18 + Vite 构建的健身房会员办卡订单管理后台。项目覆盖登录鉴权、订单筛选与分页、新建订单、跨页批量续卡、一键撤单，以及面向财务对账的受限 CSV 导出。

## 启动步骤

环境建议：Node.js 20.19+ 或 22.12+，npm 10+。

```bash
npm install
npm run dev
```

浏览器访问 `http://localhost:5173`。登录页可使用任意非空账号和密码。

常用命令：

```bash
npm run lint          # ESLint 代码检查

```

## 自动化测试与持续集成

项目使用 Vitest + React Testing Library，测试按职责分为三层：

- 纯函数测试：覆盖金额格式化、手机号格式化，以及续卡 5 年折扣边界；
- 服务测试：覆盖 36 条初始数据、分页与状态筛选、新建、续卡、撤单、鉴权和写接口校验；
- 用户行为测试：覆盖受保护路由、404、订单 Tab 筛选、续卡弹窗实时计费，以及快速查询时的请求竞态。

`npm test` 会在命令行一次性执行全部测试。`npm run test:watch` 适合开发过程，会在文件修改后只重跑相关用例。`npm run test:coverage` 会在 `coverage/` 生成 HTML 报告，可打开 `coverage/index.html` 查看每一行的覆盖情况。

覆盖率配置包含质量门槛：语句和行覆盖率不低于 60%，分支不低于 75%，函数不低于 50%。低于门槛时命令和 CI 会直接失败，避免覆盖率在后续迭代中无声下降。

仓库包含 `.github/workflows/ci.yml`。推送到 GitHub 或创建 Pull Request 时，CI 会自动执行 `npm ci` 和 `npm run check`，任何格式、Lint、测试或构建失败都会阻止质量检查通过。

## 请求层与状态管理设计

### 请求层

`src/api/http.js` 创建统一 Axios 实例：

- 使用 `/api` 作为 `baseURL`；
- 请求拦截器从 `localStorage` 读取 token，并写入 `Authorization: Bearer <token>`；
- 响应拦截器统一解包业务数据和展示错误；
- 遇到 401 时清理 Zustand 与本地 token，并重定向到 `/login`。

`src/api/mockService.js` 以 Axios 自定义 Adapter 充当内存接口层。它拥有 36 条初始订单，覆盖全部 6 种订单状态，并实现查询、分页、筛选、新建、续卡和撤单。所有写操作会真实更新模块内数据，随后查询可以看到结果；刷新页面后按题意恢复初始数据。相比在组件里直接改数组，这种方式保留了完整的请求/响应边界，也能验证拦截器行为。

### 状态管理

Zustand 只保存真正的全局状态：token、用户名及登录/退出动作。初始化时从 `localStorage` 恢复登录态。订单列表的查询参数、加载状态和结果由 `useOrderList` 管理；表单和弹窗状态保留在对应页面，避免把短生命周期 UI 状态过度提升到全局。

### 路由守卫

受保护路由由 `ProtectedRoute` 统一包裹。未登录访问 `/orders` 或 `/orders/new` 时跳转到 `/login`，并保留原目标地址；登录后返回该地址。已登录访问登录页则直接进入订单列表。

## 关键业务说明

- “进行中”包含待审核、待制卡、待寄卡。
- 列表按创建时间从新到旧展示，确保最新订单位于最前。
- 金额使用统一格式化函数；`0` 显示为 `0.00`，`null`、`undefined`、空字符串显示为 `--`。
- 续卡仅允许已到期订单；5 年及以上按 8 折计费。批量操作会明确列出不符合条件的订单号。
- 撤单仅允许待制卡、待寄卡订单，并在二次确认框中列出订单号。
- 表格使用 `preserveSelectedRowKeys` 和本地记录缓存实现跨页保留勾选。
- 新订单创建后状态为待审核，并可立即在列表首行查询到。

## 开发中最难的问题与解决过程

最难的部分是让“跨页选择”和“会改变订单状态的批量操作”同时保持正确。Ant Design 可以保留跨页的 row key，但切页后不会始终提供所有已选行的完整对象；而续卡、撤单校验又必须知道每条记录的订单号与状态。

解决过程：

1. 先把选择状态拆为 `selectedRowKeys` 与 `selectionCache(Map)`：前者驱动表格，后者缓存已选订单快照；
2. 使用 `onSelect`、`onSelectAll` 在每次勾选变化时增删缓存；加载新页后，对当前页仍被选中的记录刷新缓存，避免使用陈旧行数据；
3. 批量提交前在前端列出全部不合法订单，接口层再次做相同校验，防止绕过页面规则；
4. 成功后清空选择并重新查询，避免状态已变化的订单仍以旧状态留在后续操作集合中。

这个方案兼顾了跨页体验、错误提示所需的信息完整性和接口层的最终一致性。

## Part 5：向业务方澄清的问题

收到“给财务导出订单、金额好看一点、部分状态不能导出”的原始需求后，我会先确认：

1. 导出范围是当前页、当前筛选结果、勾选记录，还是全部订单？
2. 哪些角色拥有导出权限？是否需要细分总部财务、门店财务和运营？
3. 哪些订单状态允许导出，哪些明确禁止？状态权限是合规要求还是业务建议？
4. “金额格式好看”是需要千分位、两位小数、人民币符号，还是财务系统要求纯数字？
5. CSV 需要包含哪些字段？手机号、备注等个人信息是否允许导出或需要脱敏？
6. 导出是否应继承页面的订单号、会员姓名和状态筛选条件？
7. 单次导出是否有数量上限？大数据量时是否改为后端异步生成？
8. 是否需要记录导出人、导出时间、筛选条件等审计日志？
9. 已取消订单是否要单独用于退款核对，还是完全禁止进入本次对账文件？
10. CSV 的编码、列顺序、日期格式和文件名是否需要适配既有财务软件模板？

## Part 5：本次实现假设

在业务方未补充信息前，本项目按以下假设实现：

1. 导出按钮面向已登录后台用户开放；本题未提供角色模型，因此不额外虚构角色鉴权。
2. 导出范围为“当前 Tab + 当前订单号/会员姓名筛选条件下的全部结果”，不受当前页分页限制。
3. 只有已完成、已到期订单可以进入常规财务对账；进行中订单金额尚未最终确认，已取消订单属于无效订单，均禁止导出。
4. 当结果混有不可导出状态时，弹窗告知允许与排除的数量，用户确认后仅导出合规记录；全部不合规时不生成空文件。
5. 导出字段为订单号、会员姓名、联系电话、购卡年限、订单金额、状态、创建时间、备注。
6. 金额使用千分位并保留两位小数，例如 `12,000.00`；CSV 中不加入 `¥`，便于财务软件识别列含义并减少二次清洗。
7. CSV 使用 UTF-8 BOM，避免中文在常用表格软件中打开时乱码；文件名包含导出时间。
8. 本题的模拟数据量较小，采用前端同步导出，不设置数量上限；真实系统应在大数据量时改用后端异步任务。
9. 本题没有后端与用户权限体系，无法实现可靠审计；真实系统应由后端记录导出人、时间和筛选条件。
10. “默认按创建时间升序、最新在前”的描述逻辑存在矛盾。本实现以“最新在前”为业务目标，采用创建时间降序。
11. 续卡成功后，订单金额累加本次实际续卡费用，使金额代表该订单累计实付；原金额为空时按 0 处理。

## 工程能力补充

- 列表请求、分页、Tab 切换、搜索与刷新抽象为 `useOrderList`。
- 批量选择支持跨页保留，并可一键清空。
- Mock 层保留真实 Axios 请求链路，前端和接口层均做业务校验。
- 查询使用 AbortController 与请求序号防止快速切换筛选时旧响应覆盖新结果。
- 路由页面按需加载，并对 React、请求层依赖做稳定分包。
- CSV 对 `= + - @` 等公式前缀进行转义，降低表格软件公式注入风险。
- 页面包含加载、空结果、校验失败、成功提示、二次确认和 404 状态。
- 布局对桌面与窄屏做了响应式适配，并提供自定义 Ant Design 主题与 favicon。
- 关键业务常量、计费函数、金额格式化和 CSV 序列化均集中管理。
